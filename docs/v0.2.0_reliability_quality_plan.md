# MergeWarden v0.2.0 Reliability & Review Quality Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在保持 MergeWarden advisory reviewer 定位不变的前提下，交付“可度量、可验真、不可跳步、可恢复”的 PR 审查链路。

**Architecture:** v0.2.0 将现有五阶段 Agent Loop 扩展为候选 Finding 生成、确定性校验、独立语义验证、Review Workflow 门控和发布五个质量节点；平台侧在 SQLite 中保存运行租约与步骤 checkpoint，使 worker 崩溃后能够安全续跑。Eval 先于功能改造交付，为每项能力提供上线前后的对照基线。

**Tech Stack:** Python 3.11、Pydantic、asyncio、SQLite、FastAPI、Click、pytest、现有 OpenAI-compatible ModelClient、JSONL event log、GitHub advisory publisher。

## Global Constraints

- 对外版本采用 SemVer：`v0.2.0-alpha.1` → `v0.2.0-alpha.2` → `v0.2.0-alpha.3` → `v0.2.0-beta.1` → `v0.2.0-rc.1` → `v0.2.0`。
- 每个子版本必须可独立部署、独立关闭和独立回滚，不允许依赖未发布子版本中的数据库状态。
- MergeWarden 继续是 advisory reviewer；本版本不修改用户代码、不提交 patch、不成为 hard merge gate。
- Review 模式中的新增验证工具全部为 `ToolSafety.READONLY`，不得扩大 execute 权限。
- `ReviewResponse` 的现有必填字段保持兼容；新增审计信息进入 event log、run summary 和 eval report，不强迫现有 API 客户端升级。
- 所有新增模型循环均有确定上限：语义验证最多 1 次，补证据最多 1 次，Workflow reprompt 最多 1 次。
- `FINDING_VERIFIER_MODE=enforce`（RC/GA 默认）时，Warning 和 Critical 只有在语义验证为 `accepted` 后才能进入最终发布结果；验证失败时 fail closed，允许返回无 inline issue 的 summary。`off/shadow` 仅用于 alpha 观测和紧急行为回滚。
- 数据库升级只能使用 `CREATE TABLE IF NOT EXISTS` 和 `_ensure_column()` 兼容迁移，不删除、不重命名现有列。
- 遥测、checkpoint 或 verifier 自身故障不得产生未经验证的 GitHub 评论。
- 所有 feature flag 必须在 event log 和 run summary 中记录实际生效值。

## 1. 版本范围与非目标

### 1.1 本版本采纳范围

| 编号 | 能力 | 对应版本 | 最终状态 |
|---|---|---|---|
| P1-1 | Eval 过程质量和人工反馈闭环 | `v0.2.0-alpha.1` | GA 强制产出指标，核心质量指标进入 CI gate |
| P0-1 | Finding 独立语义验证器 | `v0.2.0-alpha.2` | GA 默认 `enforce` |

| 集成 | 回归、容量、故障注入和发布门禁 | `v0.2.0-rc.1` | 达标后发布 `v0.2.0` |

### 1.2 明确非目标

- 不实现自动修改 PR、自动提交 commit 或自动修复用户代码。
- 不建设通用 Skill 商店、通用 MCP 插件平台或五级向量记忆系统。
- 不在 v0.2.0 引入默认多 Agent 并行审查。
- 不把遥测服务可用性作为审查成功的前置条件。
- 不改变 GitHub check 的 advisory/neutral 产品定位。

### 3.2 数据契约

在 `eval/schemas.py` 增加以下模型与字段：

```python
class ReviewProcessMetrics(BaseModel):
    candidate_issue_count: int = Field(default=0, ge=0)
    evidence_bound_issue_count: int = Field(default=0, ge=0)
    verifier_accepted_count: int = Field(default=0, ge=0)
    verifier_rejected_count: int = Field(default=0, ge=0)
    verifier_needs_evidence_count: int = Field(default=0, ge=0)
    verifier_downgraded_count: int = Field(default=0, ge=0)
    first_pass_accept_count: int = Field(default=0, ge=0)
    required_step_count: int = Field(default=0, ge=0)
    completed_required_step_count: int = Field(default=0, ge=0)
    duplicate_tool_call_count: int = Field(default=0, ge=0)

    @property
    def evidence_binding_rate(self) -> float:
        return (
            self.evidence_bound_issue_count / self.candidate_issue_count
            if self.candidate_issue_count
            else 1.0
        )

    @property
    def required_step_completion_rate(self) -> float:
        return (
            self.completed_required_step_count / self.required_step_count
            if self.required_step_count
            else 1.0
        )
```

`EvalResult` 增加 `process_metrics: ReviewProcessMetrics`；`MetricSummary` 增加 suite 级平均值：

- `evidence_binding_rate`
- `verifier_accept_rate`
- `verifier_reject_rate`
- `first_pass_accept_rate`
- `required_step_completion_rate`
- `duplicate_tool_call_rate`
- `cost_per_accepted_finding`

## 9. 回滚策略

### 9.1 行为回滚

发生质量或资源问题时按以下顺序降级：

1. `FINDING_VERIFIER_MODE=enforce → shadow`：保留观测，恢复既有输出。
2. `REVIEW_WORKFLOW_ENFORCEMENT=enforce → warn`：停止 reprompt/硬门控，保留缺失步骤诊断。
3. `RUN_CHECKPOINTS_ENABLED=true → false`：停止创建新 checkpoint；已有表和列保留。
4. 若仍不稳定，回滚应用版本到最后一个已验收子版本；数据库新增列/表不删除。

### 9.2 Fail-closed 边界

以下情况即使降级也不得放行 Warning/Critical：

- 当前 run 以 `enforce` 模式启动 verifier，但 verifier 返回无效 schema。
- candidate 的证据文件或行号不存在。
- 恢复执行无法确定 GitHub publish 是否已经成功。
- Workflow 状态损坏，无法证明 `semantic_verify_findings` 已完成。

### 9.3 数据兼容

- 新版本必须能够读取没有 checkpoint 的旧 run，并视为从 `fetch_pr_context` 开始。
- 旧版本回滚后忽略新增表和列，不要求 down migration。
- artifact 和 event log 保持 append/new-file 策略，不覆盖历史基线。
