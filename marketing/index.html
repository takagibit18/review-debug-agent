Lifecycle metadata

Hidden fingerprints let later runs update matching findings and mark stale comments without editing human feedback.

mergewarden:comment dedupe stale state
.github/workflows/github-advisory.yml 
name: MergeWarden advisory
on:
  pull_request:
    types: [opened, synchronize, reopened]

permissions:
  contents: read
  checks: write
  pull-requests: write

jobs:
  advisory:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build PR diff
        run: python scripts/github_changed_lines.py --output changed_lines.json
      - name: Review diff
        run: >
          python cli.py review .
          --diff
          --output-json review_response.json
          --summary-json run_summary.json
      - name: Publish advisory
        run: >
          python cli.py github-advisory publish
          --repo "$GITHUB_REPOSITORY"
          --pr-number "${{ github.event.pull_request.number }}"
          --head-sha "${{ github.event.pull_request.head.sha }}"
          --response-json review_response.json
          --changed-lines-json changed_lines.json
          --dry-run
Dry-run is the default planning surface. Use publish mode only when the token has write permissions and the team is ready for PR feedback.

Common questions

Built to advise, not to take over your merge policy.

The product story should be conservative because the integration sits close to review authority. That boundary is part of the value.

Is MergeWarden a replacement for CI?

No. CI and branch protection remain the hard authority. MergeWarden adds advisory findings, run summaries, and review comments for risks that tests may not explain.

Why not start with a full web dashboard?

The strongest first product loop is inside GitHub PR review. A dashboard can come later for organization-level history, but the current planning keeps runtime work in CLI, API, Actions, and artifacts.

Can it comment on unchanged files?

Unchanged files can support evidence. Inline comments should stay on changed lines or changed hunks, otherwise findings remain in the check summary.

What should be built after GitHub Actions?

Comment lifecycle hardening, webhook/auth integration, async execution, durable storage, and broader operational observability are the natural next steps.
